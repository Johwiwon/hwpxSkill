# 한글 업무보고서 양식 스킬

부서 표준 보고서의 **목차 구성 · 서술 흐름 · 글꼴 규칙**을 적용한다.
HWPX 파일을 만들고 고치는 기술은 `hwpx` 스킬이 맡고, 이 스킬은 그 위에서
**무엇을 어떤 순서로 쓰고 어떤 글꼴을 입히는가**를 결정한다.

> 출처: 팀장 전달 지침(2026-09-09). 임의로 바꾸지 말고, 사용자가 다른 지시를
> 하면 그 지시를 우선한 뒤 이 문서에 반영할지 물어본다.
>
> **2026-09-22 팀장 최종본 이후**: 글꼴·크기·자간·간격·표·캡션·붙임 띠 같은
> 서식은 `team-report-hwpx` 스킬이 최종 기준이다. 새 보고서 파일은 그 스킬의
> `build_report.py` 로 만든다. 이 스킬은 절 구성·흐름·문장을 맡는다.

## 1. 양식 선택 (가장 먼저 결정)

두 가지 양식이 있다. **어느 쪽인지 확정하지 않은 채 본문을 쓰기 시작하지 않는다.**

### 양식 A — 전형적 보고서 (절을 모두 펼침)

```
제목 → 목차 → 배경 → 목적 → 현황 → 필요성(또는 문제점)
     → 개선방안(또는 추진배경) → 기대효과 → 향후계획 → 붙임
```

분량이 있고 각 절을 독립적으로 보여줘야 할 때 쓴다. 목차가 들어간다.

### 양식 B — 간소화 보고서 (관련 절을 묶음)

```
제목 → 개요(배경·목적) → 현황 및 문제점(현황·필요성/문제점)
     → 개선방안(또는 추진내용) → 기대효과 및 향후계획 → 붙임
```

괄호 안은 한 절 안에 함께 녹여 쓰는 내용이다. 기대효과·향후계획은
**추진내용 절에 녹여 넣어도 된다.** 목차 없이 바로 개요로 들어간다.

### 선택 기준

| 상황 | 양식 |
|---|---|
| 분량 5쪽 이상, 절마다 독립된 설명이 필요 | A |
| 분량 3쪽 내외, 한 사안을 빠르게 전달 | B |
| 사용자가 지정하지 않음 | **물어본다** — 임의로 고르지 않는다 |

## 2. 서술 흐름 (이 스킬의 핵심)

### 2.1 개수를 맞춘다

**문제점의 개수와 추진내용의 개수를 같게 만드는 것이 가장 좋다.**
추진내용이 더 많은 것은 괜찮다. 반대(문제점이 더 많음)는 **답하지 않은
문제가 남는다는 뜻**이므로 피한다.

```
문제점 3개  →  추진내용 3개 이상  →  기대효과 3개
문제점 3개  →  추진내용 2개                    ← 금지: 1번 문제가 방치됨
```

기대효과도 그 대응 관계를 따라간다. 각 기대효과는 어느 추진내용에서
나온 것인지 추적할 수 있어야 한다.

### 2.2 개요만 읽어도 알게 한다

**보고서를 받는 사람은 개요(배경·목적)만 봐도 무슨 이야기를 하려는지
알 수 있어야 한다.** 개요는 도입부가 아니라 요약이다. 배경에서 상황을,
목적에서 이 문서가 무엇을 하자는 것인지 밝힌다.

### 2.3 겹치는 것은 정상이다

`개요 → 현황 및 문제점 → 추진내용` 은 **내용이 많이 겹친다. 겹쳐야 한다.**
같은 사안을 점점 구체화하며 이어가는 구조이기 때문이다. 중복을 없애려고
앞에서 말한 것을 뒤에서 빼면 흐름이 끊긴다.

대신 **각 절에서 말하는 층위를 다르게 한다.**

| 절 | 층위 | 예 |
|---|---|---|
| 개요 | 무엇을 왜 | 문서 검색을 본문·유사어 검색으로 개선하려 함 |
| 현황 및 문제점 | 지금 무엇이 문제인가 | 제목에 없는 단어로는 문서를 찾지 못함 |
| 추진내용 | 그래서 무엇을 했나 | 본문 색인과 유사어 사전 적용 |
| 기대효과 | 그 결과 무엇이 좋아지나 | 문서 찾는 비율 62% → 91% |

### 2.4 흐름을 먼저 설계한다

본문을 쓰기 전에 **문제점 ↔ 추진내용 ↔ 기대효과 대응표를 먼저 만든다.**
`scripts/plan_flow.py` 로 표를 출력해 사용자와 합의한 뒤 본문을 쓴다.

## 3. 문장 작성 규칙

절 구성이 맞아도 문장이 어긋나면 보고서로 읽히지 않는다. **본문을 쓰거나
고칠 때마다 아래 네 가지를 확인한다.** 상세와 예시는
[references/writing.md](references/writing.md).

| 규칙 | 요지 |
|---|---|
| 괄호를 나열 기호로 쓰지 않는다 | `A(..)에서 B(..), C(..)` 대신 서술로 푼다 |
| 추진내용 ㅇ 에 `(라벨)`, `-` 라벨은 한 ㅇ 아래에서 통일 | 모두 붙이거나 모두 뗀다. 섞이면 독립 항목인지 알 수 없다 |
| 표 하단 `*`는 표를 읽는 열쇠만 | 결과·해석은 표 위 `-` 본문의 몫. 둘째 주석은 `**` |
| 형제 항목끼리 같은 사실을 두 번 말하지 않는다 | 같은 숫자가 두 항목에 나오면 합친다 |

**합칠 때는 기존 문장을 잘라 붙이지 말고 새로 쓴다.** 무엇을 말해야 하는지
먼저 정하고 문장을 짓는다. 세부 수치는 표와 붙임에 있으므로 본문에는
「그래서 무엇을 알았나」만 남긴다.

> 절 사이 중복(개요↔현황↔추진내용)은 정상이다(2.3). 금지하는 것은 **같은
> 절 안 형제 항목끼리의 중복**이다. 둘을 혼동하지 않는다.

## 4. 글꼴 규칙 (요약 — 상세는 team-report-hwpx)

| 위치 | 글꼴 | 크기 |
|---|---|---|
| 제목 | HY헤드라인M (장평 90) | 20pt |
| `□` 절 제목 | **HY헤드라인M** | 16pt |
| `ㅇ`, `-` 하위 본문 | **휴먼명조** | 15pt |
| 표 하단 설명(`*`, `**`) | **함초롬돋움** | 13pt(표 아래 12pt도 씀) |
| 표 안 내용 | **함초롬돋움** (머리행 굵게) | 12pt(조밀한 표 11pt) |
| 표 위 캡션 `< 제목 >` | 함초롬돋움 자간 −7 | 13pt |
| 작성일 줄 | 함초롬돋움 | 13pt |

> 2026-09-09 지침의 「표 안·표 하단 = 휴먼고딕」은 팀장 최종본(2026-09-22)에서
> **함초롬돋움으로 바뀌었다.** 휴먼고딕을 쓰지 않는다.

### 줄 채움

**두 줄로 넘어가면서 둘째 줄이 조금밖에 안 차는 상태를 피한다.**

- 한 줄로 줄일 수 있으면 → 자간을 좁힌다(팀장 최종본: 본문 −1~−16, 표 −1~−22).
  새로 만드는 문서는 `team-report-hwpx` 생성기가 자동으로 맞춘다.
- 두 줄이어야 하면 → 둘째 줄이 중간 기점을 넘도록 문장을 보강한다.

`scripts/check_report.py` 가 채움률 15% 미만(한 줄로 줄일 여지)과
15~50%(채움 부족)를 문단별로 짚어 준다. 채울 내용이 없는데 억지로 늘리지는
않는다. 팀장 최종본에도 둘째 줄이 30% 안팎인 문단이 몇 개 남아 있다.

### 문단 간격

문단 사이는 빈 문단으로 띄운다. 항목 사이 3pt(또는 5pt), 하위 항목 사이 1pt,
절 앞 10pt, 절 뒤 5pt(상세는 team-report-hwpx §4). **기존 문서를 편집할 때는
빈 문단의 크기를 함부로 바꾸지 않는다.**

적용은 `scripts/apply_fonts.py` 가 처리한다. 자세한 매핑과 HWPX 구현값은
[references/typography.md](references/typography.md) 참조.

## 5. 작업 순서

```
[1] 양식 A/B 확정            ← 사용자에게 확인
[2] 흐름 설계 (문제점↔추진내용↔기대효과 대응표) 합의
     python3 scripts/plan_flow.py --problems N
[3] 본문 작성                ← 새 문서: team-report-hwpx 의 build_report.py
                              기존 문서 편집: hwpx 스킬
[4] 구조·문장 점검
     python3 scripts/check_report.py 파일.hwpx
[5] 글꼴 적용
     python3 scripts/apply_fonts.py 파일.hwpx
[6] 배포 전 필수 게이트 (hwpx 스킬)
     python3 ~/.claude/skills/hwpx-skill/scripts/fill_hwpx.py check 파일.hwpx --strict
```

`check_report.py` 는 절 구성이 양식 A/B에 맞는지, 문제점·추진내용·기대효과
개수가 어긋나지 않는지, 개요가 비어 있지 않은지에 더해 **추진내용 절의 라벨
없는 ㅇ 항목과 한 ㅇ 아래 라벨이 섞인 `-` 항목**을 함께 짚는다. 서식(글꼴·
크기·기호) 점검은 `team-report-hwpx` 의 `inspect_report.py` 가 맡는다.

## 7. 지켜야 할 것

1. **양식을 임의로 고르지 않는다.** 지정되지 않았으면 물어본다.
2. **문제점보다 추진내용이 적으면 안 된다.** 남는 문제가 있다는 뜻이다.
3. **절 사이 중복을 이유로 내용을 지우지 않는다.** 층위를 다르게 할 뿐이다.
4. **기존 문서를 고칠 때 빈 문단 크기(3pt)를 건드리지 않는다.** 쪽 배분이 무너진다.
5. **글꼴 변경은 charPr 단위로 한다.** `<hp:t>` 를 직접 손대지 않는다.
6. **추진내용 ㅇ 에는 라벨을 붙이고, 한 ㅇ 아래 `-` 라벨은 통일한다.**
7. **표 하단 설명(`*`)에 결론을 쓰지 않는다.** 열의 뜻과 측정 조건만 남긴다.
8. **기존 문서의 자간은 charPr 을 새로 나눠서 고친다.** 공유 charPr 을 바로 고치면
   다른 문단까지 좁아진다. 새 문서는 team-report-hwpx 생성기가 문단마다 별도
   charPr 로 맞춘다.

## 8. 다른 스킬과 겹칠 때

| 주제 | 기준 스킬 |
|---|---|
| 글꼴·크기·자간·간격·표·그림·캡션·붙임 띠·제목 상자 | **team-report-hwpx** (팀장 최종본 2026-09-22) |
| 절 구성·서술 흐름·문장·라벨 | **korean-report-format**(이 문서) |
| HWPX 파일 조작, 배포 전 필수 게이트 | **hwpx** |

`hwpx` 스킬의 `references/report-style.md` 와 다른 점은 다음과 같고, 우리 부서는
team-report-hwpx 를 따른다.

| 항목 | hwpx 스킬 | **우리 부서** |
|---|---|---|
| 항목 기호 | `□ ○ ― ※` | **`□ ㅇ - *`** |
| 주석·표 글꼴 | 한양중고딕 | **함초롬돋움** |
| 문단 간격 | paraPr 문단 위 15/10/6/3pt | **빈 문단 10/5/3/1pt** |

hwpx 스킬의 `templates/report` 는 표지·목차·결재란이 붙는 정식 보고서용이다.
**우리 양식은 표지 없이 제목 상자로 바로 시작하므로 그 템플릿을 쓰지 않는다.**

**배포 전 게이트는 반드시 hwpx 스킬 쪽을 실행한다.** 이 스킬의
`check_report.py` 는 내용 구조만 보므로 파일이 한글에서 열리는지는 확인하지
않는다.
